Sprite Rendering, Blitting, and Animation
I built 2D rendering from scratch in C++, drawing images to the screen one pixel at a time without a graphics library doing the work for me, then used it to put together an actual animated scene to prove the system worked in practice.
  • The screen is really a 1D array of pixels, so I wrote the indexing math to map an (x, y) coordinate to the right spot in that array, with (0, 0) sitting at the top-left corner of the screen. That mapping is the foundation everything else is drawn on.
  • Implemented alpha blending so sprites with transparency layer correctly over what's already on screen, mixing each pixel's color by its opacity instead of drawing a hard rectangle.
  • Wrote and optimized the blit routine that copies a sprite's pixels onto the screen buffer, which is the per-frame hot path, so it had to stay fast.
  • Created a tiled background by repeating a single grass texture across the whole screen, the standard trick for filling a large area cheaply from one small image.
  • Scattered tree sprites at randomized positions so the environment looked organic instead of laid out on an obvious grid.
  • Wrote a small animation system that cycles through a sequence of fire frames on a timer, turning a set of still images into a looping flame effect.
DirectX 11 and Gateware: Cube Rendering with Camera Control
I moved from software 2D into hardware-accelerated 3D, rendering a textured cube you can fly around using DirectX 11 and the Gateware framework.
  • Wrote vertex and pixel shaders, the small programs that run on the GPU to position each corner of the cube and decide the color of every pixel it covers.
  • Set up a constant buffer to hand the world, view, and projection matrices to the GPU each frame, which is how the CPU tells the shaders where the camera is and how the scene should be projected onto the screen.
  • Built a camera system with movement controls so you can navigate around the cube in 3D space, and used Gateware to handle the window and keyboard input.
Data-Oriented Level Renderer with GPU Instancing
My most recent graphics project: a renderer that takes a level built in Blender and exported to a text file, which lists every object in the scene and the matrix describing where it sits, and draws the whole thing in DirectX 11.
  • Wrote the parser that walks the level file and resolves each entry to a mesh on disk. The level places 76 objects but only uses 13 unique models, so I keyed models by filename and let repeated placements pile up as instances on one entry, which loads each piece of geometry once instead of 76 times.
  • Laid the data out for the GPU rather than for the object graph: all 34,344 vertices and 65,736 indices are concatenated into a single vertex buffer and a single index buffer, with each model recording where its own slice begins. Every draw call then points into its region of that shared memory instead of binding new buffers.
  • Drew the level with GPU instancing, one DrawIndexedInstanced per sub-mesh that renders every copy of that model at once, so nine floor tiles cost one call instead of nine. The instance ID restarts at zero on each call, so I upload a per-draw base offset that lets each instance find its own matrix inside the shared 76-entry transform array.
  • Compiled the shaders at runtime and injected the array sizes as compile-time macros taken from the actual buffer sizes, so the arrays the shader declares can never silently disagree with what the CPU uploads to them.
